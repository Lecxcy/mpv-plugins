# split-zoom-box

tmux 式的分屏放大：把画面切成多个窗格，每个窗格显示**同一路解码**的不同区域。
因为所有窗格来自同一次解码、同一条时间轴，播放/暂停/拖进度条天然同步，不需要
任何跨窗口或跨进程的同步逻辑。分屏布局可以绑定到时间段，并像 enhanced-ab-loop
一样存档。

本插件**合并并取代了原 `drag-zoom-box` 插件**：窗格数为 1 时的行为就是原来的
框选放大。设计讨论与实测结论见 [SPEC.md](SPEC.md)，真机手动测试清单见
[TESTING.md](TESTING.md)。

## 当前状态

C++ 实现（mpv C plugin），源码见 `src/`、`include/`。分屏能力是本仓库新增的，
上游没有对应实现。

## 从 enhanced-drag 继承的行为

`meta+MBTN_LEFT` 拖拽平移也并了进来，单窗格时行为与原 enhanced-drag 完全一致：
直接写 `video-pan-x`/`video-pan-y`，从按下时的位置绝对计算，**不做任何边界
约束**（可以把画面拖到完全看不见），缩放为 0 时同样能拖。

多窗格时改为移动**鼠标所在窗格**的 `Region`——`video-pan-*` 作用在整块拼接
画面上，拖起来是所有窗格一起动，不是想要的。这条路径必然被源画面边界夹住：
窗格显示的是源画面上的一个窗口，窗口移出画面就没有内容可显示了。

## 从 drag-zoom-box 继承的行为

原 `drag-zoom-box` 的全部行为都保留在"单窗格"这条路径上，包括它相对上游
Lua 版本已经做过的三点收紧（原样承接，不再重复论证）：

- 只认两个对角线方向：**左上→右下**放大到框选范围，**右下→左上**恢复完整
  画面；两个"反对角线"、纯水平、纯垂直一律不触发任何动作。
- 两个方向都要求两个轴上的位移分别达到 4 像素阈值，恢复分支同样受保护，
  避免手抖把缩放清零。
- 拖拽中框选矩形有第三种边框颜色（`808080` 中性灰），表示"当前方向不会触发
  任何动作"。
- 几何换算用 `osd-dimensions` 的 `ml/mr/mt/mb`（mpv 已把当前 zoom/pan/rotate
  算在内的渲染矩形），不手动用 `video-zoom`/`video-pan-*` 重新推算。

原插件的按键 `Ctrl+MBTN_LEFT` 保留不变，只是绑定目标改成
`script-binding split_zoom_box/drag-select`。

## 相对 drag-zoom-box 的新增能力

### 单窗格走 video-zoom，多窗格才用滤镜

这是本插件最重要的设计决定。分屏必须靠 lavfi 滤镜（`split`→`crop`→`scale`→
`setsar`→`hstack`/`vstack`）实现，但滤镜对单区域放大这个退化情况是**降级**：

| | 单窗格（1 格） | 多窗格（>=2 格） |
|---|---|---|
| 机制 | `video-zoom`/`video-pan-x/y` | lavfi 滤镜链 |
| 硬解 | 不受影响，零拷贝 | 图头部加 `hwdownload` 回拷，不改 `hwdec` |
| 改区域开销 | 即时，逐帧可改 | 重建一次滤镜链 |
| 画质 | GPU 一次采样到窗口分辨率 | crop→swscale 到画布→vo 再缩放 |

所以插件按窗格数在两条路径之间切换，两边内部统一用归一化的
`Region{x1,y1,x2,y2} ∈ [0,1]` 表示区域，模式切换时互相换算。

### 硬解适配：不改 hwdec，改滤镜图

真硬件帧下 lavfi 的 `crop`/`scale` 会失败，而且**失败是静默的**（`vf add` 返回
success、`vf` 属性仍报告 `enabled: true`，只有日志里说被禁用）。

插件**不会改动你的 `hwdec` 设置**。它在生成滤镜图时读一次 `hwdec-current`，
当前是真硬件帧就在图头部加 `hwdownload,format=nv12|p010le`。实测真值表：

| 帧类型 | 无前缀 | 带 `hwdownload` 前缀 |
|---|---|---|
| 硬件帧 | 失败 | 成功 |
| 软件帧 | 成功 | 失败 |

早期版本是"进入多窗格时把 hwdec 切成 auto-copy、退出还原"，那个做法会**重建
解码器**，播放中反复开关会打坏 VideoToolbox 会话（`-12909` 连环解码失败），
详见 [SPEC.md §6.7](SPEC.md)。现在解码器全程不受打扰。

### 视口模型：黑边是画布的一部分

每个窗格存一个**视口**——窗格看向「源画面 + 无限黑色背景」这张画布的矩形，
允许超出源画面，超出的部分就是黑色。

- **未放大**：视口按窗格比例外扩到刚好装下整幅画面，于是显示完整画面 + 黑边。
  分屏的默认观感就该是"看得到整幅画面"。
- **框选放大**：视口内缩成窗格比例，占满窗格、裁掉多余。**框选时框住黑边，
  黑边会跟着一起放大**——它就是画布的一部分。
- **拖拽平移**：直接平移视口，不做任何范围限制，可以把画面整个拖出窗格。

因为视口比例始终对齐窗格，视口到窗格是精确的线性映射，坐标反查不需要任何
夹取。画布尺寸始终保持源的显示尺寸，所以 mpv 窗口不会因为分屏而改变大小。

### 递归二分树表达任意网格

分屏结构是 tmux 式的递归二分树（把**当前聚焦的窗格**再一分为二），不是行列
网格。这样 2x2 和不对称布局用同一套结构表达，且与嵌套 `hstack`/`vstack`
一一对应。分屏时两个子窗格都继承原窗格的区域（tmux 语义：分屏后看到的是同样
的内容）。

每个内部节点带一个分割比例，可以拖分隔条调整（默认等分），比例会被持久化；
老存档没有该字段时按等分读。

### 时间段绑定

分屏布局可以绑定到时间区间。规则刻意做得比 enhanced-ab-loop 简单——分屏不是
全程高频使用的东西，不需要那一套：

- **哪份布局生效**：播放位置落在某个段的 `[a,b]` 内就用该段的布局，否则用
  `base`（全局布局）。没有配置任何段时，`base` 就是全程生效的那份，等价于原
  drag-zoom-box 的持久缩放。
- **编辑作用于谁**：所有编辑都作用在**当前生效的那份布局**上——在段内改就是改
  那个段，段外改就是改全局。已经存在分屏段时，在段外编辑会 OSD 提示一句，
  避免误以为在改某个段。
- **创建段不影响全局布局**：早期版本会在创建段时把 `base` 清成完整画面，等于
  悄悄抹掉用户已有的全局缩放，已去掉。
- **终点必须严格晚于起点**，不做自动对调；起点落在已有段内会当场拒绝。
- **区间不允许重叠**，冲突直接拒绝。
- **没有 `enabled` 标志**：ab-loop 需要"临时禁用某段但不删"是因为循环全程高频
  使用，分屏没有这个模式。要停用就直接删。

### 进度条展示

分屏段以原生 node 发布在 `user-data/split-zoom-box/segments`，fork 的 uosc
在时间轴上画出来（蓝，当前所在的段加亮并描边）。

只有**两种区间同时存在、且时间轴是展开状态**时才上下分层（分屏在上、ab-loop
在下）；只有一种时它占满整条高度，时间轴收拢成细进度条时两者直接叠色——那里
只有一两个像素高，分层没有意义。

### 与 enhanced-ab-loop 协同

`Alt+i` 会读 enhanced-ab-loop 发布的 `user-data/enhanced-ab-loop/segments`
（原生 node 数组），把播放位置所在的那个 loop 区间原样建成一个分屏段，省得
手动对齐两个插件的起止点。对方插件没加载时属性不存在，会提示"No ab-loop
segments"，不影响本插件其他功能。

### 存档

`~~home/split-layouts/<内容哈希>.json`。两级 key 方案直接沿用
enhanced-ab-loop 的 `store`：**内容采样哈希**（文件大小 + 头尾各 64KiB）定位
存档文件，**文件名的哈希**（不是明文文件名，也不是完整路径）作为文件内部的
次级 key。完整路径既不落盘也不参与 key：它会暴露目录结构和用户名，而且移动
硬盘/NAS 换挂载点会让绝对路径整体失效。

## 按键

| 键位 | 动作 |
|---|---|
| `Ctrl+MBTN_LEFT` | 拖对角线框选：左上→右下放大，右下→左上恢复完整画面 |
| `Alt+h` | 当前窗格左右一分为二 |
| `Alt+v` | 当前窗格上下一分为二 |
| `Alt+w` | 关闭当前窗格；只剩一格时恢复完整画面 |
| `meta+MBTN_LEFT` | 拖拽平移：单窗格移动整幅画面，分屏后只移动鼠标所在的窗格 |
| `Alt+o` | 切换聚焦窗格 |
| `Alt+u` | 取消选中（收起橙色焦点框；播放时不碍事） |
| `Alt+MBTN_LEFT` | 拖窗格之间的分隔条调整大小 |
| `WHEEL_UP`/`WHEEL_DOWN` | 缩放**鼠标所在**的窗格（鼠标不在窗格内则用选中的，都没有则用第一个） |
| `Alt+,` / `Alt+.` | 设定分屏段起点 / 终点 |
| `Alt+/` | 删除当前所在的分屏段 |
| `Alt+\` | 列出所有分屏段和当前所处位置（格式与 ab-loop 的 `\` 对齐，超过 12 段时首尾各留 6 段） |
| `Alt+i` | 把当前所在的 ab-loop 区间原样建成一个分屏段 |
| `Alt+s` / `Alt+l` | 存档 / 读档 |
| `Alt+y` / `Alt+n` | 读档时"文件可能改过名"的确认（`y`/`n` 已被 enhanced-ab-loop 占用） |

分屏后聚焦的窗格会画一个橙色粗边框（画在窗格内侧，避免相邻两格的框在中缝重叠
成一条线）。焦点是**编辑期状态**：进入分屏段、读档后都不会自动选中任何窗格
（播放时不该有个框杵在画面上），`Alt+u` 可以随时取消选中。

`Alt+MBTN_LEFT` 用了修饰键而不是裸左键：mpv 的窗口拖拽（`--window-dragging`，
默认开）在 macOS 上由 Cocoa 层处理、早于 input 绑定，按住裸左键时鼠标位置
根本不会上报给插件，分隔条拖不动；裸左键还会吞掉 uosc 进度条的点击。框选作用于**鼠标按下时所在**的那个窗格，并且**会被限制在该窗格
内**——越过中缝的部分本来也会被丢掉，不如让框自己停在边界上。

框选边框颜色：绿=放大、红=恢复完整画面、灰=当前方向不会触发任何动作。
（ASS 的颜色是 `&HBBGGRR&` 字节序，早期文档把"红"误写成了"蓝"。）

## 实现说明

- 分层：`geometry.h/.cpp`（方向判定、渲染矩形换算、Region↔zoom/pan）与
  `layout.h/.cpp`（分屏树、像素分配、滤镜图生成、坐标反查、时间段）是不依赖
  mpv 的纯逻辑，`store.h/.cpp` 是不做文件 IO 的纯存档层，三者都有 Catch2
  单测；`plugin.cpp` 是唯一接触 mpv client API 的地方。
- 按键绑定：C 插件没有 `mp.add_key_binding` 的等价物，直接接住 mpv 转发的
  `key-binding` client message。`drag-select` 需要按下/松开两个边沿（`d`/`u`），
  其余按键只响应 `d`/`p`。
- 属性读取统一整个属性读成 `MPV_FORMAT_NODE` 再取字段，不用
  `mouse-pos/x` 这种子属性路径——enhanced-drag 踩过这个坑，子属性路径在实测
  环境下会静默返回 0。
- 依赖（Catch2、fmt、nlohmann/json）都走顶层 `CMakeLists.txt` 的
  `FetchContent`，理由见 [AGENTS.md](../../AGENTS.md)。

## 验证

- **单元测试**：34 个用例 / 459 条断言全部通过。覆盖方向判定与阈值边界、
  几何换算与越界裁剪、**同父窗格像素尺寸精确求和**（`hstack`/`vstack` 对此
  零容忍）、2x2 滤镜图结构、图内标签先定义后使用、坐标反查往返、分屏树的
  关闭/合并/焦点循环、存档序列化往返与损坏输入退化。
- **端到端**（`--input-ipc-server` 驱动的无窗口 mpv，实测通过）：
  - 分屏后 `vf` 出现预期 label 与图；`dwidth`/`dheight` 保持 640x360
    （`setsar` 回归）；2x2 生成两个 `hstack` + 一个 `vstack`。
  - **像素级验证**：让两个窗格都继承完整画面，截图后左右两半必须逐像素相同
    ——只看命令返回值会被"success 但没生效"骗过去（见 SPEC 的坑记录）。
  - 硬解下（`hwdec=videotoolbox`，真窗口 `vo=gpu-next`）分屏画面真的生效、
    `hwdec-current` 全程保持 `videotoolbox` 不被改动；播放中 40 次快速开关
    压测后 `Disabling filter`、`failed to decode picture` 均为 0 次。
  - 时间段：段内滤镜生效、段外自动移除。
  - 存档往返：文件写到配置目录，内容不含明文文件名或路径，删除区间后读档
    能恢复。
- **未能自动化验证**：真实鼠标拖拽路径依赖 `mouse-pos`/`osd-dimensions`，
  在 `--vo=null` 下是哑值，需要真机手测（框选手感、窗格命中、焦点框位置）。

## 已知限制

- 多窗格期间帧要经 `hwdownload` 回拷到系统内存，4K 高码率下可能有开销；
  单窗格不受影响，解码本身始终是硬件加速。理论上更优的方案是用
  `vo=gpu` 的用户着色器在 GPU 上直接合成
  （零拷贝、改区域即时生效），但 mpv 明确声明着色器语法不稳定、且只能在
  `gpu`/`gpu-next` 下用，本轮没有采用。
- 每次改窗格区域都要重建一次滤镜链（`vf-command` 对 lavfi 里的 `crop` 实测
  无效），会有一次极短的重配；拖拽期间只画 ASS 预览、松手才重建。
- 窗格显示的是**缩放后**的源区域，放大倍数过高时清晰度受源分辨率限制。
- 分屏时整块拼接画面不再叠加 `video-zoom`（否则屏幕坐标反查要多一层复合）。
- 分屏段之间不允许重叠；需要"同一时刻多套布局"的场景不支持。
