# split-zoom-box 设计说明

本文记录 split-zoom-box 的设计取舍，以及实现过程中实测出来的、与直觉相反的
平台行为。功能与按键说明见 [README.md](README.md)。

§1-§5 是功能规格，§6 是踩过的坑（每条都给现象、根因、修复、教训），§7 是
已知限制。

## 0. 背景与目标

原 `drag-zoom-box` 只能把画面放大到**一个**框选区域。实际使用中经常需要在同一
时刻关注画面里多个互不相邻的部分，但又不想开多个播放器实例各自维护进度。

目标：单进程、单 vo，把同一路解码的帧切成多个窗格，每格显示不同区域，共用
同一条时间轴；布局按时间段生效并可存档。

被否决的方案：**多开 mpv 实例 + IPC 同步进度**。每次拖进度条、变速、seek 都要
跨进程转发，还有帧级不同步的风险；而单条滤镜图天然共用一条时间轴，同步问题
根本不存在。

## 1. 渲染路径：两套机制，按窗格数切换

这是本插件的核心决定。分屏必须用 lavfi 滤镜，但滤镜对"只放大一个区域"这个
退化情况是全方位的降级：

- **硬解**：真硬件帧下滤镜直接失效（§6.4），需要在图头部加 `hwdownload`（§6.7）；
  `video-zoom` 完全不受影响。
- **画质**：`video-zoom` 是 vo 层操作，GPU 一次采样到窗口分辨率；滤镜路径是
  `crop`→swscale 放大到画布→vo 再缩放，两次重采样且第一次在 CPU 上逐帧做。
- **响应**：`video-zoom` 逐帧可改；滤镜每次改区域都要重建整条链（§6.3）。

所以：**窗格数 == 1 走 `video-zoom`/`video-pan-*`，>= 2 才挂滤镜**。
两条路径内部统一用归一化的 `Region{x1,y1,x2,y2} ∈ [0,1]` 表示"要显示源画面的
哪一块"，模式切换时互相换算，不各自维护一份坐标。

这也是 `drag-zoom-box` 能被完整吸收并删除的前提：它的行为等于本插件窗格数为 1
时的行为，没有任何退化。

## 2. 布局模型：递归二分树

任意网格不用行列网格表示，用 tmux 式的递归二分树：每次把**当前聚焦的窗格**
一分为二（左右或上下）。

理由：既能表达 2x2，也能表达不对称布局，而且与嵌套 `hstack`/`vstack` 一一对应。
`hstack` 允许各输入宽度不同、`vstack` 允许高度不同，所以将来要支持拖动分隔条
改比例，不需要改数据结构。

分屏时两个子窗格都**继承**被分裂窗格的区域（tmux 语义：分屏后看到的是同样的
内容）。未缩放时继承的就是完整画面；已缩放时不会突然跳回全图。

## 3. 滤镜图

每个窗格固定发 `crop` → `scale` → `setsar=1`，再按树形结构用
`hstack`/`vstack` 两两合并，整体是 1 进 1 出，可以作为带 label 的普通 `vf`
加载——**不需要 `--lavfi-complex`**。

```
split=2[i0][i1];
[i0]crop=W:H:X:Y,scale=w:h,setsar=1[p0];
[i1]crop=W:H:X:Y,scale=w:h,setsar=1[p1];
[p0][p1]hstack=inputs=2
```

画布尺寸取源的显示尺寸（`video-params` 的 `dw`/`dh`），保证拼接结果的显示宽高
比与原片一致；`crop` 的坐标用存储尺寸（`w`/`h`）。

**同一父节点下两个子窗格在堆叠轴上的像素尺寸必须精确求和**，靠"第二个子节点取
减法余数"而不是两边各自取整来保证（§6.5）。

## 3.1 窗格填充：放大到填满、裁掉溢出

每个窗格用 `force_original_aspect_ratio=increase` + `crop` 把区域按原比例放大到
填满窗格，超出的部分居中裁掉。

考虑过的三种做法：

| 做法 | 结果 |
|---|---|
| 直接 `scale` 到窗格尺寸 | 画面被拉变形，排除 |
| `decrease` + `pad`（保比缩小补黑边） | 窗格里大片黑边 |
| `increase` + `crop`（当前） | 填满窗格，选区超出比例的部分看不到 |

选第三种的理由：单窗格路径下同样的框选，窗口剩余空间是被**周边的真实画面**
填满的（`video-zoom` 缩放的是整幅画面，周围内容还在），看起来就是占满的；
多窗格若补黑边，两条路径观感对不上。代价是选区被裁掉一部分，这是明确权衡过的。

## 3.2 平移

`meta+MBTN_LEFT` 拖拽平移合并自已删除的 enhanced-drag，同样按窗格数分两条路径：

- **单窗格**：完全沿用 enhanced-drag 的实现，直接写 `video-pan-x/y`，从按下位置
  绝对计算，**不做边界约束**（用户明确要求过），缩放为 0 时也能拖。
- **多窗格**：`video-pan-*` 作用在整块拼接画面上，拖起来是所有窗格一起动，
  不是想要的。改成移动鼠标所在窗格的 `Region`。这条路径必然被源画面边界夹住
  ——窗格显示的是源画面上的一个窗口，移出去没有内容可显示。

多窗格平移要重建滤镜链，60Hz 重建会明显卡顿，所以限流到约 16fps，松开鼠标时
无条件补一次保证最终位置准确。

## 4. 时间段

`LayoutSegment{a, b, layout}` + 一个 `base`（全局）布局。

规则刻意做得比 enhanced-ab-loop 简单。ab-loop 那套复杂度（enable/solo/模板/
skip）是因为循环几乎全程在用；分屏是低频功能，同样的机制搬过来只是负担：

- **哪份布局生效**：落在某个段的 `[a,b]` 内用该段的布局，否则用 `base`。
- **编辑作用于谁**：作用在**当前生效的那份布局**上。段内改就是改那个段，段外
  改就是改全局；已经存在分屏段时在段外编辑会 OSD 提示，避免误以为在改某个段。
- **创建段不动 `base`**：早期版本会在创建段时把 `base` 清成完整画面，等于悄悄
  抹掉用户已有的全局缩放。这是个没跟用户确认过的副作用，已去掉。
- **终点必须严格晚于起点**，不自动对调。用户把终点设在起点之前多半是记错了
  位置，替他"猜"成反向区间不如直接拒绝让他重设。
- **起点落在已有段内当场拒绝**，不等到设终点才报重叠。
- **不做 `enabled`**：ab-loop 需要"临时禁用某段但不删"，分屏没有这个使用模式；
  加了就要维护、持久化、还要在 UI 上体现。要停用就直接删。

排序用**精确比较**，不做 epsilon tie-break：enhanced-ab-loop 早期版本在比较
函数里加容差破坏了严格弱序，是已确认的 bug。容差只允许用在"播放位置 vs 存下来
的边界"这类比较上，不能用在"存下来的值互相比较"上。

`time-pos` 用 `mpv_observe_property` 观察，但每帧回调里**不能无脑重建**：
只有生成出来的状态标识（单窗格是区域、多窗格是完整图字符串）与上次实际下发的
不同时才真正下发。这是防止每秒重建 60 次滤镜链的关键守卫。

## 5. 坐标反查

分屏生效后屏幕上显示的是**拼接画布**，不再是源画面。所以"在窗格内框选"必须
做两级反变换：

```
屏幕像素 →（osd-dimensions 的 margins）→ 画布归一化坐标
        → 命中哪个窗格（hit_test）
        → 除以窗格尺寸、经该窗格自身的 Region 映射 → 源画面坐标
```

少了这一层，第二次调整某个窗格就会取到错的区域。拖拽可能跨出窗格边界，一律
按**鼠标按下时**所在的窗格处理。

还有一层容易漏掉的：窗格用"放大到填满、裁掉溢出"的方式显示区域，所以窗格里
看到的只是区域的一个**居中子矩形**。第三步之后还要再经 `pane_visible_fraction()`
把"相对看得到那部分"的坐标折算回"相对整个区域"——少了这层，框选位置会随被裁掉
的比例整体算偏。

这一处前后改过两版，两版都出过 bug：先是保比缩放后按整个窗格算（漏掉黑边），
后来改成填满式又漏掉被裁掉的部分。教训是**显示端的每一次几何变换，反查端都
必须有对应的一次逆变换**，改了显示方式就要同步检查反查链路。

编辑期只画 ASS 预览框，**松开鼠标才重建滤镜**，避免 60Hz 重建。

## 6. 本轮实测出来的坑

以下每一条都是用真实 mpv 0.41 / FFmpeg 8.1 跑出来的，其中 4 条是"命令返回
成功但实际没生效"这类静默失败——只看返回值会被全部骗过去。

### 6.1 `setsar=1` 漏了会静默改变显示尺寸

**现象**：分屏后画面被横向拉伸，`dwidth` 从 640 变成 720。
**根因**：源的 SAR 会透过 `scale` 传下去。
**修复**：每个窗格的 `scale` 后面固定跟 `setsar=1`。
**教训**：任何"裁剪+缩放后重新拼接"的滤镜图都要显式归一化 SAR，不能假设
`scale` 会处理。单测里直接断言 `setsar=1` 的出现次数等于窗格数。

### 6.2 `vf-command` 改 `crop` 返回 success 但完全没有效果

**现象**：`vf-command <label> x 400 crop@l` 返回 `success`，画面不变。
**排查**：target 写 `crop` 或 `crop@l` 返回 success 但无效；写 `all`、`l`、
`Parsed_crop_1` 或不写则返回 `error running command`。用"两个窗格裁同样大小、
把左格命令成右格的坐标、再比较同一张截图左右两半是否逐像素相同"做帧同步判定，
确认**不相同**——命令确实没生效。
虽然 `ffmpeg -h filter=crop` 显示 `w/h/x/y` 都带 `T`（commandable）标志。
FFmpeg 8 的 `crop` 已经没有 `eval` 选项，`eval=frame` 会让整张图解析失败。
**结论**：所有区域变更一律走"用同一个 label 重新 `vf add`"的重建路径。
**教训**：滤镜参数带 commandable 标志 ≠ 通过 mpv 的 `vf-command` 能改到它；
验证必须落到像素上。

### 6.3 `vf add` 失败时 mpv 静默回滚保留旧滤镜

**现象**：加一个非法图后画面"没反应"，而不是报错。
**根因**：mpv 检测到滤镜链重建失败会撤销操作、保留上一版，`vf` 属性仍然是
旧图。命令返回值是唯一可靠的失败信号。
**修复**：`run_command` 的返回值必须检查，失败时 OSD 报错并且**不更新**内存里
的 `applied_key`，否则内存布局会和实际画面静默不一致。

### 6.4 真硬件帧下滤镜失效，且属性层面查不出来

**现象**：`hwdec=videotoolbox` 时分屏无效。日志里是：
```
Impossible to convert between the formats supported by the filter 'Parsed_crop_1' ...
Disabling filter split-zoom-box because it has failed.
```
但 `vf add` 返回 `success`，且 `vf` 属性里该滤镜**仍然报告 `enabled: true`**。
**教训**：这是最隐蔽的一条——属性层面完全看不出问题，只有日志和像素能发现。
修复方式见 §6.7（第一版的修法是错的，不要照抄）。

### 6.5 堆叠轴上尺寸差 1 像素，整张图配置失败

**现象**：`hstack` 报 `Input 1 height 360 does not match input 0 height 300` →
`Failed to configure output pad`。
**根因**：`hstack` 要求所有输入**高度**完全相同（宽度可不同），`vstack` 要求
**宽度**相同。两边各自对半取整时，奇数尺寸会差 1。
**修复**：递归分配像素时第二个子节点用 `parent - first` 取余数，从构造上保证
精确求和。单测在 640/641/1919/100 × 360/361/1081/51 的画布上逐节点断言。
**顺带确认**：奇数尺寸和奇数裁剪偏移本身是安全的（yuv420p 下
`crop=201:157:101:57`、`scale=321:360`+`scale=319:360` 拼接均成功），不需要
强制取偶。

### 6.6 `~~home/` 在没有配置目录时展开成相对路径，存档写进工作目录

**现象**：e2e 测试跑完后，存档文件出现在 mpv 的**当前工作目录**（本仓库根目录）
里，而不是配置目录。
**根因**：`--no-config` 时 mpv 没有配置目录，`expand-path ~~home/split-layouts`
返回的是 `"split-layouts"`——一个相对路径。直接拼接使用就落到了 cwd。
**修复**：展开结果必须是绝对路径，否则宁可不存并提示。
**教训**：`expand-path` 的返回值不能假定是绝对路径。同样的模式在
`enhanced-ab-loop` 里也存在（那边同样直接用 `expand_path` 的结果拼路径），
本轮没有改动那个插件，但值得后续一并加固。

### 6.7 切 hwdec 属性会打坏解码器——正确解法是根本不碰它

**现象**（用户真机反馈）：暂停时开关窗格都正常，**播放中**关窗格会连环报错，
mpv 进程还活着但画面废了：
```
Using hardware decoding (videotoolbox).          <- 插件还原了 hwdec
h264: vt decoder cb: output image buffer is null: -12909, reconfig 1
h264: hardware accelerator failed to decode picture      (连续多次)
Impossible to convert ... 'Parsed_crop_1' ...    <- 滤镜还在链上，却来了硬件帧
Disabling filter split-zoom-box because it has failed.
```

**根因**：§6.4 的第一版修法是"进入多窗格时把 `hwdec` 切成 `auto-copy`、退出时
还原"。问题在于**改 `hwdec` 属性会重建整个解码器**：

- 播放中反复重建会把 VideoToolbox 会话打坏，出现 `-12909`
  （`output image buffer is null`）的连环解码失败；
- 解码器重建和滤镜移除是两个独立的异步过程，还原 hwdec 与摘掉滤镜之间存在
  竞态窗口，硬件帧会灌进只吃软件帧的 `crop`。

暂停时不复现，是因为没有帧在流动，两个过程不会交叠。

**复现**：播放中以 ≤0.2s 的间隔反复 split/close，稳定出现
`failed to decode picture`（实测 6 次）。

**修复**：**完全不碰 `hwdec`**，改成根据当前帧类型决定滤镜图的形状。实测真值表：

| 帧类型 | 无前缀 | `hwdownload,format=nv12\|p010le,` 前缀 |
|---|---|---|
| 硬件帧（`videotoolbox`） | 失败 | **成功** |
| 软件帧（`no` / `*-copy`） | **成功** | 失败 |

没有一份图能同时兼容两种情况，所以在生成图时读一次 `hwdec-current` 来决定；
帧类型进 `applied_key`，并 observe `hwdec-current`，用户自己切 hwdec 或 mpv
自动回退时会自然重建。

修复后同样的压测（40 次快速开关）：`failed to decode picture` **0 次**，
`Disabling filter` **0 次**，解码器全程只初始化 1 次，`hwdec-current` 始终保持
`videotoolbox`。

**教训**：两条。一是**不要为了迁就自己的滤镜去改播放器的全局解码设置**——
代价是重建解码器这种重量级副作用，还引入了本来不存在的竞态；应该让自己的
滤镜去适配当前环境。二是**"暂停下测试通过"不等于通过**，这一类涉及解码/
滤镜管线的改动必须在播放状态下、并且用高频操作压过才算数。

### 6.8 早期 `hwdownload` 测试的假阴性

§6.4 记过一句"在图头部加 `hwdownload,format=nv12` 实测也失败"，**那是错的**。
当时的测试是在同一个 mpv 会话里、前一步已经把 hwdec 切走之后跑的，实际输入
已经是软件帧——而 `hwdownload` 在软件帧上本来就会失败（见 §6.7 真值表）。
在干净会话里、确认 `hwdec-current` 确实是 `videotoolbox` 时重测，前缀是好用的。

**教训**：验证平台行为时，每个用例都要在**确认过的初始状态**下跑；在一个
会话里连着测多个变体，前面的用例会污染后面的前提。一条"我试过，不行"的结论
如果建立在被污染的环境上，会把正确的方案排除掉——这次差点就是。

## 7. 已知限制（不是 bug）

- 多窗格期间帧要经 `hwdownload` 回拷到系统内存，4K 高码率下可能有开销。
  注意解码本身仍是硬件加速，且插件不会改动 `hwdec` 设置。理论上更优的是用
  `vo=gpu` 的用户着色器在 GPU 上合成（零拷贝、改区域即时生效，`PARAM` 块支持
  运行时可调参数），但 mpv 明确声明着色器语法不稳定、只能在 `gpu`/`gpu-next`
  下用，且无法在无窗口环境里自动化验证，本轮没有采用。
- 每次改区域重建一次滤镜链，有一次极短的重配。
- 窗格显示的是缩放后的源区域，放大倍数过高时清晰度受源分辨率限制。
- 分屏时整块拼接画面不再叠加 `video-zoom`。
- 分屏段之间不允许重叠。
- 真实鼠标拖拽路径依赖 `mouse-pos`/`osd-dimensions`，`--vo=null` 下是哑值，
  无法在无 GUI 环境端到端验证，需要真机手测。
