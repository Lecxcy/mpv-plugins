# split-zoom-box 手动测试指南

自动化部分（53 个单测用例 + 两套 IPC 端到端）已经跑过，覆盖范围见
[README.md](README.md) "验证"一节。**本文只列自动化测不了、或者测了也不算数的
部分**：真实鼠标拖拽、窗格命中是否准、焦点框位置、观感是否流畅。

带 `【回归】` 的用例对应 [SPEC.md](SPEC.md) §6 记录的真实坑，务必测，不要因为
"看起来是边界情况"就跳过——这几条的共同点是**命令返回成功但实际没生效**，
只有肉眼和像素能发现。

## 准备工作

### 编译并收集成可直接使用的配置目录

```sh
cmake -S . -B build
cmake --build build
scripts/collect-dist.sh
```

`dist/` 是一份完整的 mpv 配置目录，`split-zoom-box.so` 已加进 `dist/mpv.conf`
的 `scripts-append`，`dist/input.conf` 已带上全部按键绑定。

### 造一个方位分明的测试视频

分屏测试最关键的是**一眼能看出某个窗格显示的是原画的哪一块**。下面这条命令
生成 1280x720、四个象限颜色各不相同（红左上 / 绿右上 / 蓝左下 / 黄右下）、
中间有一个左右移动的 testsrc 图案（带帧计数，用来确认各窗格是否同步推进）的
30 秒素材，带音轨：

```sh
ffmpeg -y \
 -f lavfi -i "color=c=red:s=640x360:d=30:r=30" \
 -f lavfi -i "color=c=green:s=640x360:d=30:r=30" \
 -f lavfi -i "color=c=blue:s=640x360:d=30:r=30" \
 -f lavfi -i "color=c=yellow:s=640x360:d=30:r=30" \
 -f lavfi -i "testsrc=s=160x120:d=30:r=30" \
 -f lavfi -i "sine=frequency=440:duration=30" \
 -filter_complex "[0][1]hstack[top];[2][3]hstack[bot];[top][bot]vstack[grid];\
[grid][4]overlay=x='(W-w)/2+(W/4)*sin(2*PI*t/6)':y='(H-h)/2'[v]" \
 -map "[v]" -map 5:a -shortest -pix_fmt yuv420p grid.mp4
```

（这条命令刻意不用 `drawtext`——homebrew 的 ffmpeg 常常没编 libfreetype。）

启动：

```sh
mpv --config-dir="$(pwd)/dist" grid.mp4
```

### 确认插件确实加载

按 `Alt+h`，画面应立刻变成左右两格、内容相同，并弹出 OSD "分屏：2 个窗格"。
没反应先查：

- mpv 启动日志里有没有 `split-zoom-box` 或 `dlopen`/`Cannot open` 相关报错；
- `dist/plugins/split-zoom-box/split-zoom-box.so` 是否存在。

按 `Alt+w` 回到完整画面再开始正式测试。

### 定位问题用 Debug 构建

```sh
cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug && cmake --build build-debug
```

把 `build-debug/plugins/split-zoom-box/split-zoom-box.so` 换进 `dist/`，
再加 `-v --log-file=x.log` 跑。`plugin.cpp` 里 `MPV_UTIL_DEBUG` 包着的输出
（`vf add` 失败的完整 spec、存档路径展开结果）只在 Debug 下生效。

**看日志时重点盯 `Disabling filter split-zoom-box`**——这行是 §6.4 那个坑的
唯一信号，属性层面查不出来。正常情况下它一次都不该出现。

## A. 单窗格框选放大（原 drag-zoom-box 行为回归）

窗格数为 1 时本插件必须和原来的 drag-zoom-box 表现完全一致。

| # | 操作 | 期望 |
|---|---|---|
| A1 | `Ctrl+` 左键从**左上往右下**拖一个框 | 拖拽中有绿色边框跟随；松手后画面放大到框选范围 |
| A2 | 在已放大状态下再框选一次更小的区域 | 基于**当前可见画面**继续放大，不是跳回原图重算 |
| A3 | `Ctrl+` 左键从**右下往左上**拖 | 拖拽中边框是红色；松手后恢复完整画面 |
| A4 | 从右上往左下拖 / 从左下往右上拖 | 边框全程**中性灰**，松手后**什么都不发生** |
| A5 | 纯水平拖、纯垂直拖 | 同 A4，灰色且无动作 |
| A6 | 只拖 2-3 像素就松手 | 无动作（4 像素阈值），**恢复方向也一样**不触发 |
| A7 | A1 之后按 `Alt+w` | 恢复完整画面 |
| A8 | 先 `meta+` 左键拖动画面产生偏移，再按 `Alt+w` | **缩放和偏移一起清零**，画面完全复原（回归：早期版本只清缩放、偏移残留） |
| A9 | 先拖动产生偏移，再从右下往左上框选 | 同样把缩放和偏移一起清零 |

**A6 特别说明**：阈值对"恢复"分支同样生效，这是相对上游 Lua 版本刻意改的
——原版恢复分支没有下限，一像素抖动就会把缩放清零。

## B. 分屏基本操作

| # | 操作 | 期望 |
|---|---|---|
| B1 | 完整画面下按 `Alt+h` | 左右两格，**两格内容相同**（都是完整画面），OSD 提示 2 个窗格 |
| B2 | 按 `Alt+v` | 当前聚焦格再上下分成两格，共 3 格 |
| B3 | 反复按 `Alt+o` | **橙色粗焦点框**在各窗格间循环，一眼能看出选中哪格，OSD 显示"窗格 n/N"，转一圈后回到第一格 |
| B4 | 按 `Alt+w` | 关掉聚焦格，兄弟格顶替它的位置（占满原来两格的空间） |
| B5 | 一直按 `Alt+w` 到只剩一格再按 | 恢复完整画面，OSD "已恢复完整画面"，不报错 |
| B6 | 分屏后放大/缩小 mpv 窗口 | 焦点框跟着窗口重画，位置始终贴合聚焦格 |
| B7 | 分屏状态下播放 | **各窗格中间的 testsrc 图案同步移动**、帧计数一致（同一条时间轴） |
| B8 | 分屏后（**未放大**）看画面 | 每格显示**完整画面**、保持原比例，多余处补黑边；mpv 窗口大小不变 |

**B7 是这个插件的立身之本**，如果各窗格不同步就说明整个方案错了。

## C. 窗格内框选与坐标反查【重点】

这一组测的是 SPEC §5：分屏后屏幕上是拼接画布，框选必须经过两级反变换才能
换算回源坐标。**做错的话第二次调整某个窗格会取到完全错误的区域**，而自动化
测试碰不到（依赖真实 `mouse-pos`）。

| # | 操作 | 期望 |
|---|---|---|
| C1 | `Alt+h` 分成左右两格，在**左格内**框选原画的红色象限 | 只有左格变成红色特写，**右格纹丝不动** |
| C2 | 接着在**右格内**框选原画的黄色象限 | 只有右格变黄，左格保持 C1 的红色 |
| C3 | 在左格（已是红色特写）内再框选它的一小块 | 在**已放大的红色区域内部**继续放大，不是跳回全图 |
| C4 | 在右格内从右下往左上拖 | 右格恢复完整画面，左格不受影响 |
| C5 | 从左格内开始拖、拖到右格里才松手 | **框会停在中缝上、不越界**；只作用于左格，右格不受影响 |
| C6 | 框选前先按 `Alt+o` 切到另一格，再在**第一格**里框选 | 框选作用于**鼠标所在的格**，不是焦点所在的格；焦点随之跟过去 |
| C7 | 2x2 布局下，逐个在四个格里框选四个不同象限 | 四个格分别显示红/绿/蓝/黄，互不干扰 |
| C8 | 在有黑边的窗格里框选（例如左右分屏时上下有黑边），框住某个色块 | **放大后显示的就是你框的那块**，不会整体上下偏移（回归：早期版本按整个窗格算坐标，黑边越宽偏得越多） |
| C9 | 框选任意形状的区域 | **放大后**占满整个窗格，四角都是画面、没有黑边 |
| C10 | 框选一块宽高比和窗格差很多的区域 | 占满窗格，超出比例的部分被居中裁掉（这是选定的取舍，不是 bug） |
| C11 | 在已放大（有裁切）的窗格里再框选一次 | 位置准确落在你框的地方，不会因为"看到的只是选区一部分"而整体偏移 |
| C12 | **框一个很小的区域**（十几像素见方） | 正常放大，**不报错**（回归：早期版本会 `Padded dimensions cannot be smaller than input dimensions` 导致整个滤镜被禁用） |
| C13 | 框一个极细长的区域（很宽但只有几像素高） | 不报错 |
| C14 | **框选时把上下黑边也框进去** | **黑边跟着一起放大**，放大后该处仍是黑（回归：早期版本黑边会被"吸"掉，只放大画面部分） |

C7 做完的画面应该是：四个窗格各显示原画的一个象限，等于把原图"拆开又摆好"。

## E. 硬解【回归 §6.4 / §6.7】

**这一组最重要**，因为这里踩过两个坑：滤镜在真硬件帧下会被静默禁用（属性层面
查不出来，只有日志有），以及早期"自动切 hwdec"的修法会把 VideoToolbox 解码器
打坏——**暂停下完全正常，播放中反复开关才暴露**。

```sh
mpv --config-dir="$(pwd)/dist" --hwdec=videotoolbox grid.mp4   # macOS
```

| # | 操作 | 期望 |
|---|---|---|
| E1 | 启动后先看 `hwdec-current`（按 `i`） | `videotoolbox`（真硬件帧） |
| E2 | 按 `Alt+h` 分屏 | **画面真的变成两格**（不是看起来没反应） |
| E3 | 再看 `hwdec-current` | **仍然是 `videotoolbox`** ——插件不该改动你的 hwdec 设置 |
| E4 | 按 `Alt+w` 退出分屏 | 画面恢复，`hwdec-current` 依旧不变 |
| E5 | **播放状态下**反复按 `Alt+h` / `Alt+w`，快速连按十几次 | 画面始终跟得上，**不出现花屏、黑屏或卡死** |
| E6 | E5 全程看日志 | **`Disabling filter`、`failed to decode picture`、`-12909` 一次都不出现** |
| E7 | 分屏状态下播放一段 | 不卡顿、不掉帧；4K 素材下如果明显卡，记下来 |
| E8 | 分屏状态下手动切 hwdec（`i` 面板旁用 IPC 或改配置重开） | 滤镜自动按新帧类型重建，画面不坏 |

**E5/E6 是 §6.7 那个 bug 的直接回归**：修复前在播放中快速开关会稳定复现
`-12909` 连环解码失败。用 `--vo=null` 或暂停状态测**测不出来**，必须真窗口 +
播放中 + 高频操作。

**E2 如果画面没变但也没报错，就是踩到 §6.4 了**，务必反馈。

| F8 | 在已有段**内部**按 `Alt+,` 设起点 | **当场就提示"这里已在分屏段 x-y 内"**，不会等到设终点才报错 |
| F8b | 起点设在空隙、终点跨进后面的已有段 | OSD "与已有分屏段重叠，已拒绝"，已有段不受影响 |
| F9 | 段内正常播放几十秒 | **不掉帧、不周期性卡顿**——如果每秒都在重建滤镜就会有规律的顿挫 |

| F10 | 起点设在 20s，终点设在 10s | **当场拒绝**（"终点不晚于起点"），不会自动对调成 10-20s |
| F11 | 先在全局放大某区域，再创建一个分屏段，然后拖到段外 | 段外**仍是你之前的全局放大**，不会被清成完整画面 |
| F12 | 按 `Alt+\` | 列出所有分屏段、每段几格、当前所处位置（`>` 标出） |
| F13 | 已有分屏段时，在段外按 `Alt+h` | OSD 额外提示"正在编辑全局布局" |

## F1b. 把一个段切成两半（`Alt+;`）

| # | 操作 | 期望 |
|---|---|---|
| F1b-1 | 建一个 5-15s 的段并调好两个格，播到 8s 按 `Alt+;` | OSD 显示切成 `[5-8]` + `[8-15]`、共 2 段；**画面在按下的瞬间没有任何变化**（两半继承同一份布局） |
| F1b-2 | 接着在 6s 只改左格（框选放大） | 只有 `[5,8]` 这半变了；拖到 12s 看到的还是原来的布局 |
| F1b-3 | 在 12s 改右格，再拖回 6s | 两半各自保留自己的改动，互不影响 |
| F1b-4 | 按 `Alt+\` | 列出的是两段，边界正好在 8s |
| F1b-5 | 在切出来的某一半里再按 `Alt+;` | 能继续二分（切出来的半段和普通段没有区别） |
| F1b-6 | 在**段外**（比如 20s）按 `Alt+;` | OSD "No split segment here"，段数不变，不会去改最近的那个段 |
| F1b-7 | 播到**紧贴段边界**（比如 5.01s）按 `Alt+;` | OSD "Too close to the segment edge: denied"，不会产生一个比一帧还短、根本 seek 不进去的段 |
| F1b-8 | F1b-2/F1b-3 之后存档、重开、读档 | 两半各自的布局都恢复（切出来的段和普通段一样会被持久化） |
| F1b-9 | 切完之后让它从 4s **自然播过** 8s 边界 | 8s 处不出现明显卡顿或闪烁（两半布局相同时，去重守卫应该让它根本不重建滤镜） |

**F1b-9 说明**：两半布局相同的情况下，跨过边界时生成的状态标识不变，
`applied_key` 去重会挡住重建。如果这里看到闪一下，说明去重被绕过了。

**F9 是 SPEC §4 那个去重守卫的验收点**：`time-pos` 每帧都回调，但只有生成的
布局标识变了才真正下发。

## F3. 进度条展示

需要同时用到 enhanced-ab-loop。

| # | 操作 | 期望 |
|---|---|---|
| F3-1 | 只设 ab-loop 区间、不设分屏段 | ab-loop 区间**占满整条高度**，与改动前一模一样 |
| F3-1b | 只设分屏段、不设 ab-loop 区间 | 分屏段**占满整条高度**（不会只占上半条） |
| F3-2 | 两者都设 | 时间轴对半分层：**分屏段在上（蓝）、ab-loop 在下（绿）** |
| F3-3 | 播放进入某个分屏段 | 该段加亮并描边（与 ab-loop 的激活效果一致） |
| F3-4 | 全屏播放 | 底部细进度条**仍然显示**（`progress=always`），且同样带两种区间的着色 |
| F3-5 | 时间轴收拢成细进度条、且某段两种区间重叠 | 重叠处是**两色混合出的第三种颜色**（绿+蓝→青绿），不是两层叠加的糊色；只有一种区间的地方仍是它本来的颜色 |
| F3-8 | 展开态下量一下上下两条的高度 | **等高**（中线取整，不留半像素混合行） |
| F3-6 | 按 `Alt+\` 查看分屏段列表 | 竖排列出、格式与 ab-loop 的 `\` 一致；当前所在段前有 `>` |
| F3-7 | 配置超过 12 个分屏段后按 `Alt+\` | 首尾各展示 6 段，中间显示 `... (N more)` |

## 已知限制（测到这些不用报）

- **多窗格期间帧要经 `hwdownload` 回拷到系统内存**：这是刻意的，不是 bug；
  解码本身仍是硬件加速，插件不会改你的 `hwdec` 设置。4K 高码率下如果开销
  明显，属于"已知取舍"，但**具体卡到什么程度值得反馈**。
- **每次改窗格区域会有一次极短的重配**：滤镜链必须重建，`vf-command` 对
  lavfi 里的 `crop` 实测无效（SPEC §6.2）。拖拽过程中只画预览框、松手才重建。
- **窗格画质受源分辨率限制**：显示的是缩放后的源区域，放大倍数高了会糊。
- **分屏时整块拼接画面不再叠加 `video-zoom`**：这是为了让屏幕坐标反查少一层
  复合，刻意的。
- **分屏段之间不允许重叠**：同一时刻两套布局没有意义。
- 单窗格与多窗格的**画质/流畅度本来就有差别**（前者 GPU 一次采样，后者
  CPU swscale），不是缺陷。

## 反馈时最好附上

- 是哪一条用例（例如 "C5"）；
- OSD 文案现在统一是英文（与其他插件一致），看到中文提示请反馈；
- Debug 构建 + `-v --log-file=x.log` 的日志，特别是有没有
  `Disabling filter` 或 `vf add` 失败；
- 分屏当时的 `vf` 属性内容（`i` 面板或 IPC `get_property vf`）；
- 如果是画面不对，直接截图比文字描述有效得多。
